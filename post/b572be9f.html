LangChain 智能问答系统常见问题

前言

最近在折腾 LangChain 和 LangGraph，想搭一个智能问答系统。结果搭完之后发现一个很尴尬的事情：

我自己搭的系统，回答质量还不如直接把 PDF 丢给 AI 让它读。

问它问题，回答牛头不对马嘴，效果差得离谱。这让我开始反思：LangChain、LangGraph 到底在干什么？它们的作用是什么？

后来我想明白了。它们的作用是把流程组织起来（分类 → 路由 → 计算/生成），但最终答案质量取决于喂给 LLM 的上下文质量。如果检索环节把上下文搞碎了，编排得再好，LLM 也只能基于碎片回答——反而不如直接读全文。

回答的质量取决于什么

先说结论：回答的质量取决于喂给 LLM 的上下文质量。

LangChain 和 LangGraph 只是管道，它们负责把数据从 A 运到 B，但数据本身的质量才是决定性的。你管道设计得再精妙，如果流过去的是碎片化的、语义不完整的文本块，LLM 也只能基于这些碎片瞎猜。

这里有个很关键的问题：为什么所有的没有设定的问题回答的都很烂？

因为你的系统没有为这些"计划外"的问题准备路径。意图分类没覆盖到，路由走到了默认分支，检索也没针对性地取上下文，最后 LLM 只能硬着头皮编。这就是"没设定"的代价——不是 LLM 不行，是你的流程没给它铺好路。

数据向量化和文本切割到底怎么配合

文本切割太粗，检索到的上下文太泛，LLM 抓不住重点。文本切割太细，语义被切碎了，检索到的片段缺乏上下文，LLM 只能瞎编。

向量化的优势在于语义匹配——用户问"学分够不够毕业"，即使文档里写的是"毕业最低学分要求"，也能匹配上，这是关键词检索做不到的。文本切割的优势在于控制上下文长度——LLM 的上下文窗口有限，你不能把整本书丢进去，切割是为了把最相关的部分精准地喂给 LLM。

两者配合的核心思想是：使用向量化的内容定位文本段，综合它们的优势——不会出现纯向量化的差的数据质量，也不会出现大片文本里找不到所需要的信息，还能突破多文件的限制。通过向量化直接定位，一步到位。切割要保证语义完整，向量化要保证语义可匹配，这样既控制了上下文长度，又保证了检索精度。

LLM 和关键词分类该怎么搭配

LLM 负责让数据走向更……怎么说呢，更"聪明"的地方。它能理解语义，能判断意图，能处理模糊性。Python 负责……执行具体的操作。计算、过滤、排序、格式化。

在实际系统中，LLM 负责分类：这是关于什么的问题？需要检索哪些文档？Python 负责执行：根据分类结果，从向量数据库中检索，按相关性排序，格式化输出。关键是要让 LLM 做它擅长的事（语义理解），让 Python 做它擅长的事（精确计算）。

关键词分类的优势是快、准、可控、不花钱，对于"我还差多少""下学期选什么"这种固定说法，关键词匹配一秒搞定。但它的通病是太脆弱——换个说法（“我学分够不够毕业”）就可能漏，这是所有基于关键词的分类系统的死穴。LLM 理解的优势是泛化能力强，换个说法也能认出来，能处理模糊表达，但劣势是慢、贵、不稳定，同一个问题问两次可能给你分到两个类。

这里的核心是：让模糊的关键词先根据 LLM 来进行分析，确定好是否真的是匹配到了关键词，而不是有关键词就不分青红皂白地直接不管语义。 关键词匹配到一个词，不代表这个问题真的是那个类型。比如用户说"我不想要这个学分"，关键词匹配到"学分"，但用户其实是在表达意愿，不是在查询学分，这时候如果直接走学分查询分支，就答非所问了。

所以正确的做法是：关键词先筛，LLM 再判。 关键词命中后，把命中的关键词和上下文一起丢给 LLM，让 LLM 判断这是不是真的属于该类型。是，才走对应分支；不是，退回主流程或者走其他分支。高频、固定说法的问题走关键词分类，快准狠；低频、说法多变的问题走 LLM 分类，靠语义理解兜底；关键路径上的分类两者结合，关键词先筛一遍，LLM 再判断语义是否真的匹配。

和 Graph 配合时，关键词分类和 LLM 分类可以做成 Graph 里的两个节点：关键词分类是快速通道，LLM 语义确认是保险丝，LLM 分类是兜底通道。这样既保证了速度，又保证了准确性，还保证了覆盖率。

LangGraph 的工作流该怎么设置

LangGraph 的核心是什么？是数据。一切为数据服务。

流动的血液就是数据，每一次流动都是为了把更优质的数据流动到更需要的地方。

所以重要的事情有两点：

第一点，怎么让流动的数据逐渐变得优质，直到得出最优质的答案返回。

系统应该不断演化，每一步都朝着更低"能量"的方向移动，最终收敛到稳定状态。你的工作流也应该这样：每一步都让数据变得更相关、更完整、更准确，最终得到一个高质量的答案。

第二点，怎么让这个数据流向正确的地方提纯。

你需要为不同的输入设计不同的处理路径，让它们能够快速收敛到正确的结果。你的工作流也应该这样：根据问题的类型，路由到不同的处理路径，每条路径都经过精心设计，能够高效地提纯数据。

综上，核心思想是：使用 LLM 来规划数据的流向，使用结构化数据、数据的计算模块、规则算法等提纯数据，减少 LLM 幻觉。

LLM 负责判断问题类型、决定该走哪条路，这是它的强项——语义理解、意图识别、模糊判断。但数据本身的提纯不能交给 LLM，要用结构化数据、确定性计算、规则算法来保证准确性和完整性。结构化数据保证了你喂给 LLM 的上下文是干净的、完整的、准确的，不会因为切块而碎掉；规则算法保证了数值计算不会出错，不会出现 LLM 一本正经胡说八道的情况。LLM 参与数据流向的分析与管理，保证了问题能被正确地路由到对应的处理路径，不会因为关键词的机械匹配而走错路。两者结合，才能让整个系统既准确又高效。

总结

搭 RAG 系统，核心就几件事：

你需要设计一个好的工作流，让数据能够高效地流向正确的地方。你需要找到存储容量和泛化能力的平衡点（文本切割策略）。你需要让 Python 和 LLM 协同工作。你需要让 LLM 参与数据流向的分析与管理，而不是机械地依赖关键词匹配。

最重要的是，你要记住：编排只是手段，数据才是目的。

如果你的检索环节把上下文搞碎了，那再精妙的编排也救不了你。你的 RAG 系统如果处理不好数据，也会输出一堆看似合理实则胡说八道的东西。

所以，与其花时间优化工作流，不如先想想：我喂给 LLM 的上下文，质量够好吗？
